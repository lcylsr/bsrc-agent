# SRC 实战挖洞方法论（从资产到漏洞的完整思路链路）

> **定位**：具体漏洞类型（SSRF/IDOR/注入…）有各自的 skill，本 skill 补**顶层思路链路**——拿到一批资产后怎么系统化挖，从选目标到出洞的每一步该想什么。
>
> **不是流程图，是思维链路。** 每一步给方向和思路，不局限方法。AI 有自己的能力，框架确保思维链不漏环。

## Domain

- SRC 赏金平台 / 众测 / 授权渗透
- 拿到一批资产（域名/IP/APP/客户端）
- 需要产出可投递的真实漏洞（不是信息泄露报告）
- modes: src 优先（赏金驱动），pentest/redteam 通用

## Boundaries

- 无 PoC = 不报（CLAUDE.md 铁律）
- 现象 ≠ 漏洞（CLAUDE.md 铁律）
- verified 须反事实+证伪（CLAUDE.md 铁律）
- 深挖优先：广度 ≤30%，深度 ≥70%（CLAUDE.md 铁律）
- 法律红线不可妥协（law.md）

---

## 思维链路：7 环

```
环1: 资产展开 → 把"甲方+根域"变成"可打的攻击面清单"
环2: 目标筛选 → 从攻击面清单里选值得深挖的目标
环3: 切入点发现 → 对选中目标找到"第一个突破口"
环4: 深挖扩展 → 从突破口扩展到真实漏洞
环5: 验证确证 → PoC + 反事实 + 证伪
环6: 链式放大 → 单个漏洞 → 组合链 → 更大危害
环7: 复盘沉淀 → 经验写回 memory
```

**核心：不是线性走完 7 环就结束，而是每环都可能回到前一环（发现了新资产→回到环1，找到了新切入点→回到环3）。**

---

### 环 1：资产展开

**核心思路：把"甲方给的根域/IP列表"变成"全部可打的攻击面"。**

展开维度：
- **子域枚举**：被动 OSINT（crt.sh/wayback/OTX/subfinder）+ 空间测绘（FOFA/Hunter/Quake）→ 子域 >10 时 spawn recon-agent
- **端口扫描**：nmap 全端口 → 非常规端口可能有管理接口
- **Web 存活**：httpx/curl 存活探测 → 状态码/title/banner 分类
- **客户端资产**：APP（APK/IPA） / 桌面客户端（Electron/.NET） / 小程序 / API 文档
- **关联资产**：同公司其他域名 / 同 IP 其他服务 / 云存储 / CDN 源站

**思路：资产展开的目的是找"别人没想到的边角"。** 主域大家都打，但 dev/test/staging 子域、非标端口、关联公司资产、被遗忘的旧服务——这些才是出洞的地方。

### 环 2：目标筛选

**核心思路：从 N 个存活目标里选 3-5 个值得深挖的——选对目标 = 成功一半。**

筛选思路（不是机械分类，是思考"这个目标为什么值得深挖"）：
- **有后端 API 的**（不是 SPA fallback）→ 最值得深挖，API 是出洞最多的地方
- **有登录功能的**（能登录 = 认证后攻击面打开）→ 登录后测 IDOR/越权
- **有已知产品指纹的**（Spring/Struts2/Keycloak/Nacos/Druid）→ 匹配 CVE + playbook
- **有管理面板/调试接口的**（/admin /actuator /console /swagger）→ 试未授权 + 默认凭据
- **非常规端口的**（非 80/443）→ 可能有管理服务/数据库面板/内部工具
- **dev/test 环境**（测试环境安全意识弱于生产）→ 可能有弱配置/默认凭据/调试开关

**思路：不追求扫完所有目标，选 5 个深挖 > 扫 2000 个浅扫。** 广度扫描只是选目标，选完切深度模式。

### 环 3：切入点发现

**核心思路：对选中的目标，找到"第一个突破口"——不是从漏洞类型出发，是从目标特征出发。**

切入点发现思路：
- **JS 深度分析**（见 `js-deep-analysis.md` 6 维度）→ 从 JS 里提取隐藏 API / baseURL / 密钥 / 签名算法 → API 是最常见切入点
- **参数级反射**（见 `reflexes.md` 第一层）→ 看到 url/path/file/id 参数 → 直接投 payload
- **系统指纹反射**（见 `reflexes.md` 第二层）→ 看到 Spring/Struts2/.NET → 走必做清单
- **信息泄露探测**（见 `coverage-audit.md` #66-72）→ .git/.env/actuator/swagger/sourcemap → 泄露 = 切入点
- **N-day 指纹匹配**（`nday-matcher.py`）→ 指纹 → CVE → playbook
- **登录后 API 枚举**（见 `authed-deep-dive.md` 步骤 2）→ 从 JS/抓包提取全部 API → 逐个探活

**思路：切入点不一定是你"计划"找的——很多时候是"碰到的"。** 关键是对每个信号都敏感：看到参数名暗示 SSRF 就投 5 个 payload，看到 Java 技术栈就投 Log4j，看到管理面板就试默认凭据。

### 环 4：深挖扩展

**核心思路：找到切入点后不停在"发现"，要扩展到"可利用的真实漏洞"。**

深挖思路：
- **IDOR 扩展**：替换 ID → 看返回他人数据 → 试 3-5 个不同 ID → 确认是业务数据不是占位 → 反事实校验（改回自己 ID 看是否变回）
- **未授权扩展**：去 token → 200 = 未授权 → 枚举同前缀 API → 找更多未授权接口 → 证明数据泄露
- **越权扩展**：低权限 token 调管理接口 → 试 Header/路径/方法绕过 → 试 JWT 篡改升权限
- **注入扩展**：参数有注入信号 → 手工 payload 定性 → 有信号再上 sqlmap（须请示）
- **文件读扩展**：读到配置 → 找 DB 凭据/密钥 → 证明可利用（不实际连接）
- **签名绕过扩展**：提取签名算法 → 生成 replay 模板 → 去签名改参数重放 → API 仍接受 = 绕过成功

**思路：深挖不是"测更多漏洞类型"，是"把一个信号挖到能出 PoC"。** 一个 IDOR 信号 → 替换 ID → 确认他人数据 → 写 PoC → 反事实校验 → verified。不需要测完所有类型才出洞。

### 环 5：验证确证

**核心思路：从"看起来像漏洞"到"证明是漏洞"。**

验证思路（见 CLAUDE.md 铁律·无 PoC=不报 + 反事实+证伪）：
- **可重放**：curl 命令重放仍成立（不是偶发）
- **真实数据**：返回的是真实业务数据不是占位/default/SPA fallback
- **反事实 4 问**：改 ID 会怎样？无认证会怎样？假响应会怎样？假设是假的能推翻吗？
- **证伪**：假设 finding 是假的 → 写反例测试 → 反例失败（无法推翻）→ verified 成立
- **PoC 脚本**：`output/poc-<id>.py` 可执行重放
- **业务影响**：能拿到什么数据/权限/资金？定位到具体的人/订单/金额

**思路：形式合规不等于有洞。** 完整的 cURL + 字节回包 + CWE 编号看起来很专业，但如果没证明实际危害 = 垃圾洞。

### 环 6：链式放大

**核心思路：单个漏洞 → 组合链 → 更大危害 → 更高赏金。**

链式思路（见 `chain-playbook.md` 5 条链）：
- **SSRF + 云元数据** → 拿凭据 → 打内网 actuator → heapdump → token
- **任意文件读 + 配置** → DB 凭据/密钥 → 二次利用
- **信息泄露 + sourcemap** → 源码 → 代码审计 → 注入点
- **IDOR + 批量接口** → 批量数据 → PII 影响
- **认证绕过 + 管理面板** → 配置修改 → 持久化

**思路：链式不是后置报告整理——是前置攻击假设。** 看到 SSRF 信号时，同一时刻就在想"SSRF→169.254→凭据→actuator"。每发现一个 candidate 立即问"能接上哪条链？"

### 环 7：复盘沉淀

**核心思路：每个目标测完后，经验写回 memory 防止下次重蹈覆辙。**

复盘思路（见 `orchestrator.md` 收尾&复盘）：
- **中标经验** → `memory/playbooks/`（可复用打法）
- **误测/漏测/盲区** → `memory/reflections/`（认知教训）
- **证伪指纹** → `memory/rejected/`（防重复踩坑）
- **通用模式** → `memory/insights/`（方法论提炼）
- **核心问题**：这个洞为什么现在才出现？哪个环节如果早点做就能更早发现？

## 思维链路的关键节点

### "切换信号"——什么时候换环

不是走完环 1 才进环 2，有信号就切：
- 发现 API 路径 → 环 1 跳到环 3（切入点发现）
- 能登录 → 环 2 跳到环 4（深挖：认证后 IDOR）
- 发现 403 → 环 4 内部 pivot（不换环，换角度）
- 发现 ≥2 verified → 环 4 跳到环 6（链式放大）
- 死磕 30 分钟无果 → 环 4 跳到环 2（换目标）

### "深挖 vs 广扫"——什么时候停广度切深度

- 选完 Top 5 目标 → 立即停广度（环 1/2 结束）
- 对每个目标找到切入点 → 停找新切入点（环 3 结束），开始深挖（环 4）
- 广度时间 ≤ 总时间 30%
- 深挖时间 ≥ 总时间 70%

### "放弃信号"——什么时候换目标/换方向

- 同一目标 20-30 分钟无新信号 → 换目标（环 2 回环 1 选新目标）
- 同一攻击面 5-8 次尝试无果 → 标 Dead End，换攻击面
- 遇到 SPA fallback → 跳过（不深挖 SPA）
- 遇到 WAF 封禁 → 切换攻击面（IDOR/逻辑类 WAF 不拦）
- 30 分钟死磕无果 → _STATE.md 写"待决问题"问用户

## SRC 主奖品分布（优先级参考）

```
RCE / 任意文件读 / SSRF / 上传 ≫ SQLi / IDOR ≫ 认证绕权 / 弱随机 ≫ 信息泄露 / 配置类
```

**思路：不是按这个顺序测，是按这个顺序"优先深挖"。** 看到 SSRF 信号优先深挖，看到安全头缺失不深挖（垃圾洞清单处理）。但切入点是"碰到什么测什么"——不是"计划测 SSRF 所以只找 SSRF"。

## Common misses

- **广度有余深度不足** → 扫 2000 个目标 0 verified，不如深挖 5 个目标
- **遇到 403 就停** → 权限校验是信号不是终点，思考校验在哪层能不能换层绕过
- **只测一个 baseURL** → 同一 API 不同域名权限可能不同
- **JS 只 grep /api/** → API 可能在对象属性/拼接/常量里，不只 /api/ 前缀
- **不试 JWT 篕改** → 拿到 token 后每个字段都是可测维度
- **看到 SPA 还深挖** → 所有路径返回同一 HTML = 没有后端 API，跳过
- **形式合规当漏洞报** → cURL+CWE 看起来专业但不证明危害 = 垃圾洞
- **链式后置** → 看到 SSRF 不想链，等 verified 才想 = 错过组合拳时机
- **不复盘** → 下次重蹈覆辙，经验不沉淀

## Verification

- **verified**：PoC 重放 + 真实数据 + 反事实 4 问 + 证伪 + 业务影响
- **candidate**：有信号但 PoC 未闭合 / 反事实未通过
- **phenomenon**：有响应但无业务影响（安全头/CORS 无敏感API/版本号）
- **rejected**：证伪成功 / SPA fallback / default 占位

## ⚠️ 红线

- 无 PoC = 不报
- 现象 ≠ 漏洞
- GET 只读免请示，POST 写/重武器须请示
- 不破坏/不批量拉取/不下载源码
- 用测试小号 + 无害 payload + 测完清理
