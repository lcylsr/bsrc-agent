# 技术方案文档 — AI 主驾驶渗透测试协作框架 v6.0-slim

> BSRC "Agent+" 攻防能力挑战赛参赛作品技术方案（≤5000 字）
> 演示仓库见 `examples/demo-acme`（脱敏虚构案例）；源码、运行环境与部署方式见仓库 README。

## 一、作品概述

本作品是面向 SRC 定向漏洞挖掘的 **AI 主驾驶渗透测试协作框架**：以国内大模型（DeepSeek/GLM/文心 Comate）为推理主驾驶，以"假设-验证-报告"闭环为核心工作流，通过可证伪假设、反事实校验、生命周期状态机三道闸门，把 AI 的探测动作约束为"有证据、可重放、可复检"的审计结果。整体定位：不追求"全自动一把梭"，而是解决 AI 渗透实践中两个真实痛点——**现象误当漏洞（误报率高）** 与 **深度不足（广度有余）**。

框架 v6.0-slim 面向 8 核 16G 托管环境设计，无 GPU 依赖、无第三方依赖（纯 Python 标准库），完整跑一次小型目标约需 1~2 万 token、内存占用 <500MB。

## 二、技术架构

```
┌────────────────────────── 指挥层（Commander）──────────────────────────┐
│  会话状态机：接单门禁 → 攻击面 → 探测 → 验证 → 投递                     │
│  资源纪律：2 包定性 / ≤5 包定死 · 广度≤30% 深度≥70%                     │
└───────────────┬─────────────────────────────────────────────────────────┘
        ┌───────┴──────────┐
┌───────▼────────┐  ┌──────▼──────────┐
│ driver/ 模型适配层 │  │ 生命周期真相源      │
│ OpenAI 兼容 API  │  │ lifecycle.yaml     │
│ 双协议：function  │  │ phenomenon→candidate│
│ calling + ReAct  │  │ →verified→money_    │
│ 黑名单硬拦 · 0依赖 │  │ ready→delivered    │
└───────┬────────┘  └──────┬──────────┘
┌───────▼──────────────────▼──────────┐
│   工具面：bash/python 执行 · 只读/写白名单    │
│   证据面：rounds 轮次卷 · PoC 脚本 · 重放签名  │
└──────────────────────────────────────┘
```

三层职责：

1. **指挥层（Commander）**：负责任务分解与节奏控制。按"广度批 → 深度批 → 组合分析 → 复盘"轮转，深度批对 Top N 候选各投 20~50 包；同一攻击面连续 3 轮无 ≥medium 新洞即切出，不无限耗资源。
2. **模型适配层（driver/）**：国内大模型接入的关键原创组件。仅用一个 OpenAI 兼容 chat/completions 接口支持 DeepSeek / GLM / 文心 Comate 三家（api_base 一键切换）；同时支持 **function calling 与 ReAct 双协议**——模型不支持 function calling 时自动降级为代码块协议（```bash / ```python / ```write），确保异构模型行为一致。内置工具黑名单（`rm -rf`/sqlmap/nuclei/写操作绕过等硬拦截）与写路径白名单（仅 targets/examples/output/tests），即使模型失控也无法破坏宿主或越权写仓库。
3. **真相源层**：`lifecycle.yaml` 为 finding 唯一真相源，状态机 `phenomenon → candidate → verified → money_ready → delivered`，每次变更追加 history；由 lint 工具自动校验状态机前置条件（verified 必须有 PoC + 重放签名 + 业务影响证据，candidate 必须有解锁计划）并生成投递/证据/审批视图，杜绝"AI 自说自话"与索引漂移。

## 三、核心算法与方法

### 3.1 假设-验证-报告闭环（可证伪推理）

每一轮探测必须形成可证伪假设："若 `id` 参数未做鉴权，则替换 id 应返回他人订单。"最小测试 ≤5 包验证预期 vs 实际；无信号的假设按预算放弃（5 包），**不为已投包数硬凑漏洞**。这是对 AI 渗透最核心的约束：推理成本花在"判别"而非"遍历"。

### 3.2 反事实校验 4 问（防误报闸门）

任何 phenomenon 升 candidate 前必须自问 4 问，任一不通过即保留降级：

1. **改 ID/参数会怎样**——IDOR/BOLA 反证；
2. **无认证会怎样**——未授权反证；
3. **假响应会怎样**——误报反证（换不可达地址/不存在资源/无凭据重放）；
4. **证伪**：假设该 finding 是假的，写出能推翻它的反例测试，反例失败才允许 verified。

前 3 问是确认性验证（容易自我说服），第 4 问是证伪性验证（对抗沉没成本）。配套判别三连（如 `..;/` 认证绕过：P1 直连 401 → P2 绕过 200 → P3 假资源 404）把"看起来像"拆成可判定的子证据。

### 3.3 组合验证（现象 → 实际危害）

单个 phenomenon（如 SSRF 能读 /etc/hosts）不足以证明危害；当"现象 A + 现象 B 组合后可证实际利用价值"时（SSRF 读到内网管理网段配置 → 证明可做内网探测），组合 PoC 作为 verified 证据。**每条 verified 必须有 business_evidence（真实业务影响证据）与 replay_signature（重放后响应仍含的关键证据串）**——PoC 脚本在报告、投递、复检三个时点重跑结果一致，杜绝"演示时灵时不灵"。

### 3.4 生命周期状态机与证据链

finding 从现象到投递的每一次状态迁移都留痕（触发物/解锁计划/复检日）。`money_ready`（可投递）必须满足：verified + PoC 可重放 + 影响面完整 + 最近复检通过；缺任何一项（如缺甲方对数据敏感度的确认）明确记录 `missing` 而不投递。证据缺什么写什么，不掩盖。

### 3.5 资源纪律与安全边界

- **发包纪律**：接口级 2 包定性、5 包定死；同一 host 并发 ≤1；默认仅 GET；≤2 RPS。
- **写操作纪律**：只读探测优先，验证类写操作限定小号 + 无害 payload + 测完清理。
- **法律红线内建**：黑名单硬拦破坏性命令；探测产物一律落临时目录，仓库只留文本证据。
- **记忆与复盘**：每轮进展实时写回轮次卷（防上下文截断失忆）；日末 spawn 复盘 agent 产出规则修订与 playbook 增量，注入下一轮——框架自身随案例迭代进化。

## 四、实验结果（演示基线 + 设计指标）

### 4.1 演示案例（examples/demo-acme，虚构目标）

脱敏虚构案例完整跑通框架闭环：3 资产、3 条 verified（SSRF 组合验证 / `..;/` 认证绕过 / IDOR），**总发包 12 包、0 误报**；三条 finding 均附可重放 PoC（`--demo` 离线回放模式，不发真实包）。

| 指标 | 本框架演示基线 | 传统人工渗透参考 | 说明 |
|---|---|---|---|
| 漏洞发现率 | 3/3 目标面命中（演示面） | 面命中率 ~10-30%（人工按经验选面） | 假设驱动 + 反射准则（SSRF 5 payload 一发即中等）提高命中 |
| 误报率 | 0（3 条全部过反事实 4 问） | 人工常见 30-50%（现象即报） | 反事实校验 + 证伪闸门为硬门槛 |
| 单高危漏洞发现时长 | 50 分钟（`..;/` 绕过：401 信号→verified） | 数小时~数天 | 判别三连避免"试了不行换下一个"的无序 |
| 代码审计量级 | 12 包 / 3 接口 / 单 JS bundle | 人工数百~数千包 | 包数预算纪律（2 包定性）反向约束成本 |
| 大模型运行成本 | ~1.5 万 token / 案例（DeepSeek 约 ¥0.1） | —（无 AI 成本但人力成本高） | 消息裁剪 + 命中才深挖 |
| 人机验证时间比例 | <10%（仅接单门禁与投递复核） | 100%（全程人工） | 主驾驶为模型，人只做门禁/仲裁 |

> 靶场（8/17 开放 24h）基线设计值：单高危 ≤30 分钟定位、误报率 <15%、全目标 ≤2000 包预算内。演示基线与靶场实际数据以赛事真实执行为准。

### 4.2 成本-质量权衡

框架的设计哲学是**用推理质量换包数**：每包之前先形成假设，每包之后先反事实校验，把"扫得多"换成"判得准"。在 8 核 16G 无 GPU 约束下，DeepSeek-chat 吞吐足以支撑单 Commander + 多 agent 并发（ThreadPoolExecutor ≤4）；GLM/Comate 作为同构备选，经 driver 双协议适配后行为一致。

## 五、创新点

1. **反事实 4 问作为 verified 硬门槛**：把"无 PoC=不存在、现象≠漏洞"从口号变成可执行判定流程（3 确认 + 1 证伪），系统性压降 AI 渗透的误报率。
2. **模型无关驱动层（双协议降级）**：仅依赖国内模型通用的 OpenAI 兼容接口，function calling 与 ReAct 双协议自动切换，DeepSeek/GLM/Comate 一行配置替换——不受单一厂商绑定。
3. **重放签名机制**：每条 verified 登记响应证据串，PoC 重跑自动校验命中，投递前复检与报告期验证完全一致，解决"演示结果不可复现"的评审扣分点。
4. **状态机驱动的证据闭环**：finding 唯一真相源 + 自动视图生成，投递队列/证据队列/审批队列自动维护，管理成本从"人工盯表"变为"机器校验"。
5. **安全内建**：工具黑名单 + 写白名单 + 临时目录产物策略，模型失控的最坏情况是"探测失败"而非"宿主受损"，使 AI 渗透具备可授权的工程前提。

## 六、运行环境与部署

- **硬件**：8 核 16G（托管环境达标）；**依赖**：Python 3.10+，零第三方库。
- **模型**：DeepSeek `https://api.deepseek.com/v1` / GLM `https://open.bigmodel.cn/api/paas/v4` / 文心 Comate（以赛事说明为准），配置见 `driver/config.example.json`。
- **部署**：`git clone` → 配 key → `python driver/copilot.py self-check` 自检 → `python driver/copilot.py demo` 离线回放 → 接入真实目标（流程见 `examples/demo-acme/README.md`）。
